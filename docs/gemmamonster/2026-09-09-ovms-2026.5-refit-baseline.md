## 3. Current architectural authorities

The following responsibility boundaries are considered intentional and should not be duplicated during the comparative refit.

### Generation grammar

`Gemma4GenerationConfigBuilder` owns request-to-generation-grammar construction.

It currently owns:

- `auto` tool grammar construction;
- `required` tool grammar construction;
- named-tool restriction;
- request tool-schema projection into structural tags;
- `parallel_tool_calls` to `stop_after_first` mapping;
- hard-choice fail-closed behavior after structured-output validation failure.

`buildTriggeredToolGrammar()` is an intentional primitive and must not be removed merely because another runtime expresses lazy tool triggering differently.

### Rendered-prompt adaptation

`ChatTemplateProcessor` is the single authority for adapting already-built hard Gemma4 grammar after the final chat template is rendered.

Production entry point:

`adaptGemma4HardToolGrammarForRenderedPrompt()`

The duplicate `Gemma4GenerationConfigBuilder::adaptConfigForRenderedPrompt(...)` implementations and the builder-local rendered-prompt heuristic were removed. Do not reintroduce a second rendered-prompt authority without concrete evidence that the production render boundary cannot express a required behavior.

### Tool parsing

`Gemma4ToolParser` owns Gemma4 native tool syntax and executable-call validation.

The production registry-aware path distinguishes canonical tool syntax from recovery syntax. Bare `call:` handling is tolerance/recovery, not the canonical Google Gemma4 protocol.

### Reasoning orchestration

`Gemma4ReasoningParser` owns Gemma4 reasoning delimiters and reasoning payload semantics.

`OutputParser` owns cross-parser phase orchestration. A direct tool opener before an explicit reasoning close may be handled only as parser-configured tolerance/recovery. Canonical Google Gemma4 closes `<channel|>` before `<|tool_call>`.

### Token decoding and phase boundaries

`OVMSTextStreamer` owns phase-aware detokenization and special-token visibility. Parser-specific alternate streamer architectures are out of scope unless a later failing test demonstrates that the existing seam cannot represent a required behavior.

## 4. Frozen behavior contracts

Any comparative implementation proposal from llama.cpp, vLLM, SGLang, or another server must preserve these properties unless a new evidence-backed design explicitly replaces one.

### Parser invariants

The existing suite covers and therefore treats as protected behavior:

- recursive native arrays, objects, and scalar values;
- preservation of nested scalar types;
- literal braces, brackets, and JSON-like text inside native strings;
- parenthesized argument containers where accepted by the current recovery contract;
- anchored colon-name compatibility form;
- canonical reasoning-to-tool transitions;
- bounded direct-call recovery after reasoning;
- request tool-registry enforcement;
- unknown tool rejection as non-executable output;
- malformed-call containment so a later valid call can still survive;
- truncated arguments producing no executable tool call;
- consecutive tool calls with contiguous indices and distinct IDs;
- literal `<tool_call|>` inside JSON/native strings remaining payload;
- JSON escapes and Windows path preservation;
- every-byte split tolerance for complete calls;
- non-Gemma reasoning not inheriting Gemma4 takeover semantics;
- numeric literals beyond machine integer/float precision remaining lexically preserved;
- long-running parser buffer compaction without invalidating already-emitted owned deltas;
- false bare-call prose such as `call:question prose` remaining content;
- split bare-call recovery such as `call:quest` followed by `ion{...}` remaining recoverable.

### Generation invariants

The existing generation contracts protect:

- no-tools / `tool_choice=none` behavior;
- Gemma4-specific structured-output fail-closed policy for hard tool choice;
- hard choices allowing complete reasoning before mandatory tool selection on a new turn;
- `auto` permitting ordinary prose while constraining a tool call once the trigger occurs;
- named-tool selection restricting the available executable tool tag;
- `parallel_tool_calls` mapping consistently into grammar repeatability;
- actual schema strings remaining intact through structural-tag construction;
- impossible hard choice rejection;
- active tools and `response_format` not silently replacing one another;
- invalid tool names and empty tool schemas being rejected.

### Render-boundary invariants

The current contract requires hard Gemma4 grammar to be adapted after chat-template rendering when the rendered prompt already ends inside an open thought channel.

The adaptation must preserve:

- tool registry restriction;
- required/named hard-choice semantics;
- `parallel_tool_calls` / single-call policy;
- fail-closed validation behavior.

### Streamer invariants

With `skip_special_tokens=true`, canonical reasoning close followed immediately by `<|tool_call>` must still be visible to the parser as a valid phase transition. The streamer must synchronize phase-required decoding before deciding whether the current token itself is a phase opener.

## 7. Comparative-refit change envelope

The incoming parser/generator research report should classify each external technique as one of:

1. **Already present / equivalent** — no code change.
2. **Gemmamonster currently stronger** — retain local implementation and document why.
3. **Worth transplanting** — first add a failing characterization/regression test, then make the smallest implementation change.
4. **Incompatible with current OVMS/OpenVINO GenAI contracts** — reject unless a concrete local failure justifies architectural change.
5. **Dangerous regression** — explicitly record why the external implementation would weaken a frozen invariant.

Preferred modification order:

1. `src/llm/io_processing/gemma4/gemma4_tool_parser.{hpp,cpp}`
2. `src/llm/io_processing/gemma4/gemma4_reasoning_parser.{hpp,cpp}`
3. `src/llm/io_processing/generation_config_builder.hpp`
4. `src/llm/io_processing/input_processors/chat_template_processor.{hpp,cpp}` only for genuine render-boundary issues
5. `src/llm/io_processing/output_parser.cpp` only for cross-parser orchestration defects
6. `src/llm/ovms_text_streamer.{hpp,cpp}` only for demonstrated decode/phase defects

Do not introduce a generic new parser framework, parallel streamer, or second rendered-prompt authority merely to mirror another model server's architecture.

## 8. Planned remaining iterations before local deployment

### Iteration A — comparative transplant

For each high-value finding from the external parser/generator analysis:

1. reproduce the missing or incorrect behavior against this baseline;
2. add the smallest failing contract test;
3. implement only the behavior required by the test and source evidence;
4. run the complete relevant contract target set;
5. commit one logical behavior change at a time.

### Iteration B — candidate hardening

After comparative transplantation stops producing clearly justified improvements:

- consolidate canonical vs recovery behavior;
- run adversarial chunk-boundary cases;
- run malformed-output containment cases;
- verify special-token phase boundaries;
- verify request tool-registry enforcement;
- verify multi-tool and single-tool policy;
- verify rendered-prompt continuation cases;
- make no new architectural expansion unless a failing acceptance case requires it.

## 9. Local-machine acceptance gate

The eventual local candidate must be tied to one exact source SHA throughout build, tests, launch, and evidence collection.

Minimum gate sequence:

1. build the exact candidate SHA with the Windows OVMS toolchain;
2. execute `scripts/gemma4/test-protocol-hardening.ps1` against binaries from that same SHA;
3. launch the same binary with the intended Wondernuttz Gemma4 OpenVINO model;
4. run REST smoke for `auto`, `required`, named-tool, `parallel_tool_calls=true`, and `parallel_tool_calls=false`;
5. test canonical reasoning -> tool and tool-result -> next-generation loops;
6. run malformed/recovery cases separately from canonical protocol cases;
7. run long CodeSleuth-style prompts;
8. run at least one real CodeSleuth or NovaClaw/OpenCode tool loop;
9. record exact source SHA, binary provenance, OVMS/OpenVINO version, model path/revision, launch profile, and test results in the acceptance evidence.

Only after that gate should a later ref be described as a known-good local Gemmamonster candidate.

## 10. Handoff rule for the incoming research report

The next implementation session must read this freeze note and the external comparison report from exact repository refs before editing code.

The external report is input evidence, not an authority that automatically overrides working local behavior. Current local behavior remains authoritative where it is covered by stronger contracts or demonstrated live-agent requirements.

The expected end state is not “Gemmamonster looks more like another server.” The expected end state is a smaller, better evidenced parser/generator delta that preserves the working OVMS 2026.5 integration and improves behavior that can be demonstrated by tests or live acceptance.
