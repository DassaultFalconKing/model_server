# Gemmamonster 2026.4 Capital Refit Architecture

Status: architectural inventory

Comparison authority:

- upstream 2026.4 source base: `9eb93f15fecb848d399f17c7a6a6626e5a1498d7`
- accepted advanced semantic authority: `fde0762ba314dc5f6448726dfce7c533bad9a8a6` plus its Gemma4 protocol-hardening ancestry
- stable refit line: `integration/gemmamonster-2026.4-latest-refit`
- event-model contract: `docs/gemmamonster/INTERNAL-EVENT-MODEL.md`

The refit is not “OVMS 2026.5 with an older version number”. It is a selective architectural forward-port: advanced Gemma4 protocol, generation, API-policy and session-continuity behaviour is carried onto the last maintainer 2026.4 source base while retaining the 2026.4 runtime envelope. The explicit goal is to preserve the functionality needed by local agents without inheriting the problematic 2026.5 runtime/GPU layer on the target Arc system.

## 1. What changed at capital scale

The work falls into nine architectural slices.

### 1.1 Gemma4 native protocol engine

Primary files:

- `src/llm/io_processing/gemma4/gemma4_tool_parser.cpp`
- `src/llm/io_processing/gemma4/gemma4_tool_parser.hpp`
- `src/llm/io_processing/gemma4/gemma4_reasoning_parser.cpp`
- `src/llm/io_processing/gemma4/gemma4_reasoning_parser.hpp`

The tool parser is the largest protocol rewrite in the refit. Relative to the upstream 2026.4 base, `gemma4_tool_parser.cpp` changes by more than one thousand lines of churn. It is no longer a thin format adapter. It is a model-native protocol state machine responsible for:

- Gemma4 tool-call framing;
- native argument parsing;
- nested objects and arrays;
- quoted strings and special marker-like text inside payloads;
- lexical number preservation;
- tool registry validation;
- bounded bare-call recovery;
- repeated calls to the same tool;
- incremental `ToolCallDelta` emission.

The reasoning parser is likewise model-native rather than inherited from a Qwen-style implementation. It understands the Gemma4 thought channel and cooperates with tool-call transitions.

Capital ownership change: Gemma4 protocol meaning is owned by Gemma4 parsers rather than inferred by endpoint serializers or generic OpenAI logic.

### 1.2 Parser-owned boundaries and generic phase orchestration

Primary files:

- `src/llm/io_processing/output_parser.cpp`
- `src/llm/io_processing/output_parsing_config.hpp`

New/strengthened configuration semantics include:

- `needsSpecialTokens`;
- `ownsToolCallBoundaries`;
- `defaultDecodingWithSpecialTokens`;
- `toolStartTerminatesReasoning`.

This creates an explicit distinction between:

- the generic phase orchestrator, which owns phase lifecycle and buffering;
- a model-specific parser, which may own the literal protocol delimiter for its phase.

For Gemma4, the tool parser can own `<|tool_call> ... <tool_call|>` framing. The generic router must therefore avoid stripping or replaying the same boundary. The reasoning parser can also declare that a tool start is an implicit reasoning terminator.

Capital ownership change: phase routing remains generic, while boundary interpretation becomes configurable and parser-owned.

### 1.3 Guided generation becomes a Gemma4 policy engine

Primary files:

- `src/llm/io_processing/generation_config_builder.hpp`
- `src/llm/io_processing/base_generation_config_builder.hpp`

`Gemma4GenerationConfigBuilder` now owns request-to-grammar translation for tool calling.

It implements:

- `auto` with `StructuredOutputConfig::TriggeredTags`;
- `required` and named tool choice with hard structured grammar;
- optional complete thought channel before a mandatory tool call;
- named-tool restriction;
- fail-closed validation for hard choices;
- response-format/tool-constraint conflict rejection;
- invalid/unknown tool-name rejection;
- `parallel_tool_calls` propagation into `stop_after_first`;
- repeated same-tool support by duplicating the sole structural tag when parallel calls are allowed.

The last item is especially important. Repeated calls are not modeled as “same function, same call”. Grammar permits multiple applications; parser/emitter identity is carried by tool-call index/ID.

Capital ownership change: request tool policy becomes generation-time grammar policy rather than a best-effort parser expectation after unconstrained decoding.

### 1.4 Rendered prompt-state reconciliation

Primary files:

- `src/llm/io_processing/chat_template/analyzer.cpp`
- `src/llm/io_processing/chat_template/caps.hpp`
- `src/llm/io_processing/input_processors/chat_template_adapter.cpp`
- `src/llm/io_processing/input_processors/chat_template_adapter.hpp`
- `src/llm/io_processing/input_processors/chat_template_processor.cpp`
- `src/llm/io_processing/input_processors/chat_template_processor.hpp`

This is a major two-stage ownership model.

Before rendering, the generation builder knows request intent: tools, tool choice, parallel policy, response format.

After Jinja rendering, only the template processor knows the actual continuation state. In particular, the rendered prompt may already end inside the Gemma4 thought channel.

The refit therefore adds post-render adaptation so the effective hard grammar and parser start state match the rendered prompt. This prevents duplicate thought openers and similar impossible grammars.

Capital ownership change:

- request intent owner: generation builder;
- rendered continuation-state owner: chat-template processor/adapter;
- final grammar must reconcile both.

### 1.5 Special-token streamer handoff

Primary file:

- `src/llm/ovms_text_streamer.cpp`

The streamer is the decode/transport seam between GenAI token IDs and semantic parsing.

The refit strengthens it for Gemma4 reasoning-to-tool transitions by preserving special-token boundaries that may otherwise disappear under normal skip-special-token decoding. It cooperates with parser phase configuration and token-ID boundary detection.

Capital ownership change: special-token visibility is a transport/parser-correctness concern, not an endpoint formatting concern.

### 1.6 OpenAI request policy and public emitters

Primary files:

- `src/llm/apis/openai_api_handler.hpp`
- `src/llm/apis/openai_request.hpp`
- `src/llm/apis/openai_completions.hpp`
- `src/llm/apis/openai_responses.hpp`
- `src/llm/apis/openai_responses.cpp`

The refit adds/strengthens:

- `parallel_tool_calls` request policy with OpenAI-compatible default `true`;
- type validation of that policy;
- propagation into generation policy;
- fail-closed rejection of hard/named tool choice when no tools exist;
- endpoint output reflecting the actual parallel policy.

The internal `Delta` event algebra and `DeltaChannel` transport are inherited from upstream 2026.4. The refit preserves that seam and makes Gemma4 correctness flow through it instead of emitting endpoint JSON from model parsers.

Public emitter ownership remains endpoint-specific:

- Chat Completions handler owns Chat Completions JSON/chunk structure;
- Responses handler owns Responses output-item lifecycle, SSE event names, sequence numbers, accumulated reasoning/content/tool-call state and terminal events.

Capital ownership change: protocol parsing stays below `Delta`; public wire emission stays above it.

### 1.7 Persistent session continuity

Primary files:

- `src/llm/servable.cpp`
- `src/llm/servable.hpp`

This is the largest non-Gemma-specific architectural addition.

New types:

- `SessionTurnContext`;
- `SessionStateStore`.

The store is process-wide and disk-backed. It is activated through `OVMS_SESSION_STORE_DIR` and keyed by `X-OVMS-Session-ID`.

Responsibilities include:

- session ID validation;
- persistent per-session seed;
- seed-conflict rejection;
- monotonically numbered turns;
- raw request journal;
- effective request journal after session adaptation;
- generation-config journal;
- atomic file replacement;
- storage quota;
- request-size quota;
- bounded in-memory LRU metadata cache;
- model/last-access metadata.

The execution context carries only a lightweight `SessionTurnContext`; request bodies remain in the disk-backed store.

Capital ownership change: multi-turn continuity becomes an explicit servable/session responsibility. Parser state and endpoint-emitter state remain per-response and must not leak across turns.

### 1.8 Stable runtime and package provenance layer

Added files:

- `scripts/gemmamonster/stable-runtime-profiles.ps1`
- `scripts/gemmamonster/build-stable-candidate.ps1`
- `scripts/gemmamonster/launch-stable-candidate.ps1`
- `scripts/gemmamonster/Test-StableCandidate.ps1`
- `scripts/gemmamonster/test-stable-source.ps1`
- `scripts/gemmamonster/audit-stable-refit.ps1`

Modified packaging file:

- `windows_create_package.bat`

The stable line treats source provenance, dependency provenance, packaged-runtime provenance and runtime acceptance as separate facts.

Two runtime profiles are defined:

- latest maintainer 2026.4 RC2;
- historical known-good 2026.4 RC1 for A/B comparison.

The source tree is not rewritten to switch profiles. Build/package tooling verifies exact dependency fingerprints and packaged DLL hashes, restores build-mutated source files, requires a clean tree, emits manifests/provenance records, and checks that loaded runtime modules resolve from the candidate package.

Capital ownership change: runtime identity is owned by reproducible profile/package metadata, not inferred from the source branch name or an `ovms.exe` lying around on disk.

## 4. Emitter map

The refit has three emitter layers.

### Semantic emitters

Model-specific parsers return typed `Delta` values:

```text
ContentDelta
ReasoningDelta
ToolCallDelta
FinishDelta
```

`AudioDelta` belongs to the common upstream event algebra but is not Gemma4-specific.

### Transport emitter

`OVMSTextStreamer` decodes token output, preserves phase-critical special-token boundaries, invokes `OutputParser`, and forwards produced deltas through the callback into `DeltaChannel`.

### Public emitters

Chat Completions and Responses handlers translate the same semantic deltas into different wire protocols. Responses additionally owns its public lifecycle state, including sequence numbering and output-item initialization/finalization.

## 5. Why this is “2026.5-functionality on 2026.4” rather than a full downgrade/upgrade

What was deliberately carried forward:

- hardened Gemma4 model-native parsing;
- reasoning/tool phase interoperability;
- guided tool grammar;
- hard/named/auto tool-choice semantics;
- repeated/parallel tool-call policy;
- post-render prompt-state adaptation;
- streaming special-token handoff;
- OpenAI ingress/egress policy;
- persistent multi-turn session continuity;
- acceptance/provenance discipline around the runtime candidate.

What was deliberately **not** imported as the foundation:

- the OpenVINO/GenAI 2026.5 runtime dependency switch;
- 2026.5 package/version pins;
- unrelated upstream 2026.5 changes;
- experimental GPU/cache/runtime tuning that is not required for the protocol contract.

The source base remains the last maintainer 2026.4 commit before the upstream runtime switch. The default stable runtime profile remains maintainer 2026.4 RC2, with RC1 retained only as an exact known-good A/B oracle.

## 6. Architectural risk ranking

Highest-risk slices:

1. `SessionStateStore` / `servable.cpp`, because it adds process-wide durable state, disk IO, locking, quotas and request mutation.
2. Gemma4 tool parser, because it is a large protocol state machine and directly controls tool identity/arguments.
3. generation grammar, because an invalid structured grammar can turn a semantically correct request into HTTP failure or impossible generation.
4. post-render prompt adaptation, because it crosses template and generation ownership.
5. streamer special-token handoff, because a one-token decode difference can destroy a phase boundary.

Lower blast-radius but contract-critical:

- OpenAI `parallel_tool_calls` policy;
- Responses/Chat serialization of already-correct deltas;
- runtime provenance scripts and package verifier.

## 7. Forward-port rule

Future OVMS upgrades should be evaluated by ownership slice, not by file replacement.

For every upstream candidate, independently compare:

```text
runtime/GenAI
request policy
generation grammar
prompt-state adaptation
special-token decode seam
phase orchestrator
Gemma4 reasoning parser
Gemma4 tool parser
Delta transport
Chat emitter
Responses emitter
session owner
package/provenance owner
```

Replace a Gemmamonster slice only when upstream has an equivalent or stronger ownership contract plus evidence for the same acceptance cases. A later version number is not sufficient evidence.
