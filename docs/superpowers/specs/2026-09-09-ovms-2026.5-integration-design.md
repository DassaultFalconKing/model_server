# OVMS 2026.5 Integration Design

## Purpose

Move Gemmamonster from the current known-good OpenVINO/GenAI 2026.4 line to the OVMS/OpenVINO 2026.5 line without sacrificing the validated Gemma4 tool-calling, parser, generation-policy, session, and deployment behavior that currently works on Windows/Intel Arc.

This is an integration migration, not a rewrite and not a history rebase.

## Frozen refs

- Gemmamonster known-good source: `c48366fee1f10cdf6b5fe3c181522ed0c58fc9fd`
- Freeze ref: `freeze/gemmamonster-2026.4-known-good`
- Integration branch: `integration/ovms-2026.5`
- OVMS upstream merge base: `e894bac71dc02616a68b669af7445a0f8fdb3361`
- OVMS upstream 2026.5 candidate head: `b935fe8b96a0445f3746297f872b55ed202fa6e5`
- Upstream delta from merge base: 13 commits

`main` remains the product known-good line and MUST NOT move until the 2026.5 candidate passes acceptance.

## 2026.5 dependency set

The candidate must use the coordinated dependency set pinned by upstream OVMS at the selected head:

- OpenVINO: `9b1d5c9494e838d42b5ed90d662c8ce84e5742f8`
- OpenVINO Tokenizers: `4813f2b8dac54c4946ed76d91709f949dfad5455`
- OpenVINO GenAI: `2e3b291a30e84fa067b042e35b8826d18d273882`
- package line: `2026.5.0.0.dev20260903`

The migration MUST NOT update only `versions.mk` while retaining old OVMS source behavior. OVMS, OpenVINO, GenAI, and Tokenizers are treated as one compatibility surface.

## Integration strategy

Use a merge-based upstream intake on `integration/ovms-2026.5` rather than rebasing the 95 Gemmamonster commits.

Reasons:

1. The existing commit history is evidence of the parser/generation/session investigation and must remain inspectable.
2. The upstream delta is small relative to the Gemmamonster history.
3. Merge resolution makes upstream-vs-overlay ownership explicit.
4. Future migrations can repeat the same procedure with a new integration branch.

## Ownership rules

### Take upstream by default

The following areas are upstream-owned unless a concrete Gemmamonster compatibility regression is demonstrated:

- OpenVINO/GenAI/Tokenizers pins and package URLs
- product version metadata
- generic OVMS server lifecycle and servable-management changes
- generic OpenAI API changes unrelated to Gemma4 compatibility
- generic packaging and build-system changes

### Preserve Gemmamonster semantics until proven redundant

The following behavior is overlay-owned until upstream passes the same acceptance contracts:

- Gemma4 bounded/recursive tool parsing
- guarded recovery behavior
- request tool-registry validation
- hard/named/required tool-choice fail-closed semantics
- guided-generation constraints needed for reliable tool calls
- direct-call and reasoning-to-call transitions
- Google-template/session compatibility
- persistent multi-turn effective configuration behavior
- Windows Gemma4 deployment/profile helpers
- Gemma4 acceptance and reliability harnesses

An upstream implementation may replace local code only when the same contract tests pass and the local behavior is demonstrably redundant.

## Migration phases

### Phase 1: Freeze and provenance

Keep `freeze/gemmamonster-2026.4-known-good` pinned at the exact known-good SHA. Record all migration refs in this spec and subsequent acceptance evidence.

### Phase 2: Semantic three-way analysis

For each relevant overlapping file, compare:

1. merge-base behavior;
2. Gemmamonster known-good behavior;
3. upstream 2026.5 behavior.

Classify every material Gemmamonster change as one of:

- `UPSTREAM_SUPERSEDES`
- `KEEP_OVERLAY`
- `ADAPT_OVERLAY`
- `TEST_ONLY`
- `DOC_OR_EVIDENCE_ONLY`

No parser/generation/session code is removed solely because upstream now has similarly named functionality.

### Phase 3: Upstream intake

Merge exact upstream head `b935fe8b96a0445f3746297f872b55ed202fa6e5` into `integration/ovms-2026.5`.

Resolve conflicts according to the ownership rules above. Do not merge the integration branch into `main` during this phase.

### Phase 4: Build and contract recovery

Acceptance order:

1. Windows build
2. server startup and `/v1/models`
3. standalone Gemma4 parser corpus
4. `tool_choice=auto`
5. `tool_choice=required` and named/hard choice
6. guided generation
7. multi-turn/session behavior
8. chained tool calls
9. reliability campaign
10. long-context profile and 64K default behavior
11. OpenCode/NovaClaw local-agent smoke tests

Failures are fixed on the integration branch and must be tied to reproducible evidence.

### Phase 5: De-overlay

After the 2026.5 candidate is green, compare local Gemmamonster behavior with upstream implementations again. Remove local runtime code only where upstream is contract-equivalent. Keep useful acceptance tests even when implementation code disappears.

### Phase 6: Promotion

Promotion to `main` requires:

- build PASS;
- parser contract PASS;
- tool-call reliability at least equal to the frozen known-good baseline;
- no regression in required/named fail-closed semantics;
- successful multi-turn tool chain;
- recorded exact OVMS/OpenVINO/GenAI/Tokenizers provenance;
- review of the final local overlay surface.

## Long-term branch model

- `main`: latest accepted Gemmamonster product state
- `freeze/gemmamonster-2026.4-known-good`: immutable rollback/reference line for this migration
- `integration/ovms-2026.5`: active 2026.5 integration line
- future migrations: `integration/ovms-<version>` created from the then-current accepted `main`

The project should evolve toward a thin reliability overlay on upstream OVMS rather than a permanent broad fork. Runtime patches should shrink when upstream proves equivalent; acceptance evidence and deployment tooling remain first-class project assets.
