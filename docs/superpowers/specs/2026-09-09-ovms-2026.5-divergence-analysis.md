# Gemmamonster vs OVMS 2026.5 Divergence Analysis

## Scope

This report compares the frozen Gemmamonster known-good state with the selected OVMS 2026.5 upstream candidate using the shared merge base.

Refs:

- merge base: `e894bac71dc02616a68b669af7445a0f8fdb3361`
- Gemmamonster known-good: `c48366fee1f10cdf6b5fe3c181522ed0c58fc9fd`
- upstream OVMS 2026.5 candidate: `b935fe8b96a0445f3746297f872b55ed202fa6e5`
- upstream delta: 13 commits
- Gemmamonster delta from merge base: 95 commits

The goal is not to maximize upstream adoption. The goal is to take upstream 2026.5 where it is authoritative while preserving local behavior that has stronger tested semantics.

## Classification legend

- `UPSTREAM_SUPERSEDES`: take upstream behavior and drop/avoid local duplicate.
- `KEEP_OVERLAY`: local behavior remains materially stronger or is absent upstream.
- `ADAPT_OVERLAY`: both sides contain useful, non-equivalent changes and must be composed.
- `TEST_ONLY`: retain as acceptance/evidence, not runtime product logic.
- `DOC_OR_EVIDENCE_ONLY`: preserve for provenance/history only.

## Executive findings

1. Upstream 2026.5 does not directly modify `src/llm/io_processing/gemma4/` in its 13-commit delta from the shared merge base.
2. Upstream still ships the simpler Gemma4 tool parser. The Gemmamonster parser is materially more defensive: recursive native value parsing, nested containers, lossless number handling, guarded bare-call recovery, and request-tool-registry enforcement.
3. Upstream `GenerationConfigBuilder` does not route `toolParserName == "gemma4"` to a Gemma4-specific generation builder. Gemmamonster does, and implements auto/hard structured-output grammars and fail-closed required/named behavior.
4. Upstream adds useful generic features around reasoning effort and chat-template tool-definition response fields. These should be adopted, but they do not replace the Gemmamonster Google-template/session workarounds.
5. The highest semantic collision risk is at API/template integration boundaries, not in the parser core.

## Detailed semantic observations

### 1. Gemma4 parser remains a real fork

The upstream parser still relies on specialized string normalization helpers such as `parseArrayParameter`, `parseObjectParameter`, `normalizeArgStr`, and a simpler streaming state machine.

The Gemmamonster parser has moved beyond that design. Its current implementation includes:

- recursive parsing of native Gemma4 argument values;
- nested object and array support;
- preservation of numeric lexical form instead of round-tripping through floating-point or fixed-width integer DOM types;
- bounded detection of container termination;
- guarded recovery of native bare `call:` leaks only from logical line boundaries;
- validation of recovered names against the request tool registry when enforcement is enabled;
- explicit protocol-marker handling beyond the simple start/end tool tags.

This is not duplicate code with different formatting. It is a stronger parser contract.

### 2. Guided generation is a major local capability, not upstream duplication

The selected upstream `GenerationConfigBuilder` supports model-specific builders for Llama3, Qwen/Hermes3, Phi4, and Devstral, but not Gemma4.

Gemmamonster adds a dedicated `Gemma4GenerationConfigBuilder` with three policy modes:

- disabled;
- auto;
- hard.

For `auto`, it uses structural triggered tags so ordinary text remains legal until the Gemma4 tool-call trigger appears, after which tool name/schema are constrained.

For `required` and named choices, it builds mandatory tags, respects `parallel_tool_calls`, and allows Gemma4's optional thought channel before the mandatory tool call.

For hard choices, structured-output validation failure is intentionally fail-closed: the grammar is not silently removed and generation is not allowed to fall back to unconstrained text.

This behavior is central to the known-good acceptance result and must survive the 2026.5 migration.

### 3. Chat-template changes must be composed

Upstream 2026.5 introduces a useful `supportsResponseFieldInToolDefinition` capability and removes unsupported `response` fields from tool definitions before templating.

Gemmamonster independently introduced `parseToolResponseJsonContent` for templates that can consume mapping-valued tool results. The local analyzer deliberately refuses that conversion when a template uses the problematic parts scan (`part.get('type')`), because Jinja can iterate mapping keys and then invoke `.get()` on strings.

The correct integration is therefore not ours versus theirs. The integrated cap set should retain both independent capabilities, and the adapter should perform both transformations where their respective flags are active.

### 4. Parallel tool-call policy is tied to generation semantics

Gemmamonster makes common tool parsing virtual and overrides it in chat completions to parse `parallel_tool_calls` before common schema/tool-choice processing.

That value is consumed by the Gemma4 structural grammar to select `stop_after_first` behavior. Dropping the override while keeping the generation builder would silently change semantics even if compilation succeeded.

This is exactly the kind of migration regression that a textual conflict resolver will not find for us, because apparently software still expects humans to understand software.

## Expected conflict policy for the first exact-SHA merge

### Prefer upstream

- `versions.mk`
- product/version metadata
- package and Docker dependency versions
- generic server/servable lifecycle refactors
- upstream reasoning-effort support
- upstream generic chat-template response-field support
- additive common utilities

### Prefer Gemmamonster behavior

- `src/llm/io_processing/gemma4/gemma4_tool_parser.*`
- Gemma4-specific generation policy in `generation_config_builder.hpp`
- required/named fail-closed behavior
- hard-choice missing-tool validation
- `parallel_tool_calls` parsing semantics needed by Gemma4 grammar
- Google-template guarded tool-response conversion

### Compose manually

- `src/llm/apis/openai_api_handler.*`
- `src/llm/apis/openai_completions.hpp`
- `src/llm/io_processing/chat_template/caps.hpp`
- `src/llm/io_processing/chat_template/analyzer.cpp`
- `src/llm/io_processing/input_processors/chat_template_adapter.*`
- `src/BUILD` and related BUILD targets if both sides touched dependency wiring

## Acceptance implications

The first 2026.5 build is not accepted merely because it compiles. The migration must explicitly demonstrate that the following local contracts survived:

1. hard/named choice without usable tools fails rather than becoming unconstrained generation;
2. `parallel_tool_calls=false` still maps to one-call structural behavior;
3. auto mode permits normal prose but constrains a started tool call;
4. required/named mode cannot fall back to free text after grammar validation trouble;
5. nested/native Gemma4 arguments still parse losslessly;
6. guarded bare-call recovery does not turn prose examples into executable calls;
7. Google-template tool-result chaining still survives request 2+;
8. the frozen parser/reliability corpus remains green before promotion.

## Current recommendation

Proceed with an exact-SHA upstream merge only after this design/divergence set is reviewed. During merge resolution, treat the classification table above as the ownership map. Do not remove local Gemma4 runtime code merely because upstream exposes the same parser name or a neighboring generic feature.

After a green 2026.5 candidate exists, run a second de-overlay review. That is the correct time to delete local code proven redundant by contract tests.
