# OVMS 2026.5 Forward-Port Execution Plan

## Objective

Build a new Gemmamonster 2026.5 candidate on the exact latest upstream OVMS `main` verified for this session while keeping the working 2026.4 line untouched and preserving only the Gemma4 reliability overlay that upstream still lacks.

Verified upstream head at execution start:

- `openvinotoolkit/model_server:main`
- SHA: `b935fe8b96a0445f3746297f872b55ed202fa6e5`
- upstream version line: `2026.5.0`
- package set: `2026.5.0.0.dev20260903`
- OpenVINO: `9b1d5c9494e838d42b5ed90d662c8ce84e5742f8`
- GenAI: `2e3b291a30e84fa067b042e35b8826d18d273882`
- Tokenizers: `4813f2b8dac54c4946ed76d91709f949dfad5455`

Frozen known-good source remains:

- `c48366fee1f10cdf6b5fe3c181522ed0c58fc9fd`
- `freeze/gemmamonster-2026.4-known-good`

`main` MUST NOT move during this plan.

## Strategy

Use an upstream-first forward-port rather than resolving the whole 95-commit historical delta textually.

1. Start the runtime tree from exact upstream `b935fe8b...`.
2. Add only Gemmamonster runtime behavior classified `KEEP_OVERLAY` or `ADAPT_OVERLAY`.
3. Preserve the previous integration/docs lineage as an additional parent of the synthesized integration commit so provenance remains inspectable.
4. Keep the 2026.4 freeze independent for immediate rollback and A/B comparison.

## Task 1: Establish 2026.5 runtime baseline

Create a dedicated forward-port branch from exact upstream SHA.

Target branch:

- `integration/ovms-2026.5-forward-port`

Baseline acceptance before overlay:

- confirm tree contains upstream `versions.mk` 2026.5 pins;
- confirm product/version metadata is upstream 2026.5;
- do not copy 2026.4 package URLs or source pins.

## Task 2: Add RED migration-contract tests before runtime overlay

Port/create focused tests that describe the local behavior missing from upstream. Tests are migration authority and must precede production overlays.

Required contracts:

1. Gemma4 parser handles nested native objects/arrays.
2. Gemma4 parser preserves large/precise numeric lexical values.
3. guarded bare `call:` recovery accepts only the intended native leak shape and validates names against the request registry.
4. `tool_choice=required` or named choice without usable tools fails closed.
5. Gemma4 `auto` uses triggered structural tags and still allows normal prose before the trigger.
6. Gemma4 hard choice uses mandatory structural tags and optional thought-channel composition without an empty `ConstString`.
7. hard-choice structured-output validation failure cannot clear the grammar.
8. `parallel_tool_calls=false` reaches the generation policy and sets single-call behavior.
9. Google-template/tool-response mapping conversion remains guarded against templates that iterate parts and call `part.get('type')`.

Prefer existing Gemmamonster tests where they already encode these contracts; do not invent duplicate weaker tests.

## Task 3: Port Gemma4 parser core

Port the known-good Gemmamonster parser implementation on top of upstream 2026.5:

- `src/llm/io_processing/gemma4/gemma4_tool_parser.cpp`
- `src/llm/io_processing/gemma4/gemma4_tool_parser.hpp`
- preserve upstream reasoning parser unless a concrete local delta is required;
- preserve required BUILD wiring and parser tests.

Do not replace the hardened parser with upstream's older state-machine implementation merely because both are named `gemma4`.

## Task 4: Port Gemma4 generation policy

Port the minimal builder changes required for Gemma4 guided generation:

- `src/llm/io_processing/base_generation_config_builder.hpp`: model-specific validation-failure policy hook;
- `src/llm/io_processing/generation_config_builder.hpp`: `Gemma4GenerationConfigBuilder`, Gemma4 routing, auto/hard grammar, fail-closed unset policy.

Retain upstream 2026.5 generic decoding/MTP/DFlash behavior from the upstream base implementation.

## Task 8: Static verification before claiming runtime readiness

Because GitHub-side source editing does not prove compilation, perform repository-level checks that are possible here:

- verify integration head ancestry contains exact upstream SHA and previous integration lineage;
- verify upstream `versions.mk` values are present unchanged;
- verify all required overlay symbols/paths exist;
- verify old 2026.4 package pins are absent from the 2026.5 runtime tree;
- verify `main` and freeze ref remain unmoved.

Do NOT claim BUILD PASS until an actual Windows/Linux build run supplies exit-code evidence.

## Task 9: Inspect and update launch/deployment scripts

After runtime forward-port is assembled, inventory launch/deployment/profile scripts in the fork and compare them with 2026.5 upstream behavior.

Goals:

1. make 2026.5 build/package paths default to the new upstream-compatible dependency line;
2. keep an explicit 2026.4 known-good path/profile for A/B comparison;
3. keep the same Gemma4 model/profile knobs wherever semantics are unchanged;

5. ensure scripts do not silently point at an old OVMS binary after rebuilding 2026.5;
6. preserve the existing 64K context default where it belongs to Gemmamonster deployment policy, unless upstream 2026.5 requires a different hard limit.

Deliver an A/B operator path that can start either:

- known-good 2026.4 Gemmamonster;
- candidate 2026.5 Gemmamonster;

against the same model and comparable REST acceptance harness.
